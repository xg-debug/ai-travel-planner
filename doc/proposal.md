## 2. 项目背景

旅游规划是一个典型的多约束决策问题。用户在出行前通常需要同时考虑目的地、日期、人数、预算、兴趣偏好、天气、景点距离、餐饮、住宿、开放时间、路线顺序和避坑信息。传统攻略或搜索工具可以提供大量信息，但用户仍然需要自己筛选、比较、排序和组合，最终才能形成一份真正可执行的行程。

“随心游”的目标不是简单给用户推荐几个景点，而是利用 AI 的自然语言理解、任务拆解、工具调用、候选排序和方案生成能力，帮助用户从“我想去哪儿玩”快速得到一份适合自己、路线合理、预算清晰、可编辑、可导出的旅行计划。

当前项目已经具备微信小程序规划入口、后端 FastAPI 服务、LangGraph `TripPlanningWorkflow` 规划链路、地图/天气/POI/预算等能力。后续需要将现有能力产品化，明确第一阶段需求边界，并向生产级智能旅游规划助手演进。

## 3. 产品定位

“随心游”定位为：

**面向全体用户的 AI 智能旅游规划助手。**

第一阶段聚焦：

**国内单城市 1-7 天游，支持城市、日期、人数、预算、旅行偏好输入，生成可执行行程，并支持编辑行程与导出图片或 PDF。**

产品核心价值：

1. 降低用户做攻略的时间成本。
2. 将零散推荐整合为可执行行程。
3. 根据用户预算、偏好、天气、路线顺序生成更合理的安排。
4. 给出推荐理由和避坑提醒，让用户知道为什么这样安排。
5. 支持用户二次调整和导出保存。

## 4. 当前系统现状

### 4.1 已完成能力

当前代码已经具备以下基础能力：

1. 小程序端规划入口：支持输入目的地或需求、选择开始/结束日期、人数、预算和旅行偏好。
2. 小程序端生成进度页：展示“拆解旅行需求、搜索景点、安排餐饮、推荐住宿、评估动线”等步骤。
3. 小程序端结果展示：支持行程详情、地点详情、地图预览、天气、预算和历史行程。
4. 后端 API：提供行程规划、行程保存、历史行程、天气、路线等接口。
5. 后端智能规划：使用 `TripPlanningWorkflow`、Planner、Executor、Replanner、Finalizer 等模块完成 Plan-Execute-Replan 闭环规划。
6. 外部数据：已接入高德 POI、天气、酒店/地图相关服务，并有预算估算和图片补全能力。

### 4.2 目前智能体现

当前系统的智能主要体现在：

1. **任务拆解**：不是直接让大模型生成全文，而是将旅行规划拆成景点、餐饮、酒店、动线、POI 补全、审查等子任务。
2. **工具增强**：通过地图、天气、POI 等真实数据辅助生成，降低纯大模型幻觉风险。
3. **流水线分工**：不同步骤负责不同规划环节，降低单一提示词复杂度。
4. **结果审查**：Reviewer 节点对行程完整性、重复、明显冲突进行检查。
5. **结构化输出**：输出 itinerary、天气、预算、推荐、酒店等可被小程序渲染的数据结构。

### 4.3 当前不足

当前系统距离生产级智能旅游规划助手仍有以下差距：

1. 自然语言理解能力仍偏基础，模糊需求缺少标准处理流程。
2. 推荐排序逻辑尚未形成明确评分模型，结果可信度和可解释性不足。
3. 天气、开放时间、预算、路线对行程生成的影响还不够明确。
4. 生成结果仍偏“一次性生成”，用户编辑、调整和导出闭环不足。
5. 异常兜底、质量评估、日志监控和数据可信度机制还需要生产化。
6. 酒店、餐饮、避坑提醒等模块需要更清晰的产品边界。

## 5. 目标用户

“随心游”面向全体用户，但第一阶段优先覆盖以下用户：

| 用户类型 | 典型需求 | 产品价值 |
| --- | --- | --- |
| 自由行新手 | 不知道怎么安排路线 | 快速生成可执行行程 |
| 周末/短途出游用户 | 想快速规划 1-3 天行程 | 降低决策成本 |
| 情侣/朋友出游用户 | 希望兼顾体验和预算 | 平衡景点、餐饮、路线 |
| 家庭用户 | 希望节奏合理、不折腾 | 控制行程强度和交通距离 |
| 攻略参考型用户 | 需要一个高质量草案 | 可编辑、可导出、可二次调整 |

第一阶段不支持多人偏好冲突处理。例如多人分别设置不同偏好、权重投票、协作编辑等能力不纳入 MVP。

## 6. 产品目标

### 6.1 用户目标

1. 用户输入城市、日期、人数、预算和偏好后，能快速得到一份 1-7 天可执行行程。
2. 用户能理解每个推荐为什么适合自己。
3. 用户能看到每日预算和总预算。
4. 用户能根据天气、路线和避坑提醒调整出行预期。
5. 用户能编辑最终行程，并导出为图片或 PDF 保存。

### 6.2 产品目标

1. 从“景点推荐”升级为“完整旅行规划”。
2. 建立明确的推荐评分与排序机制。
3. 将天气、路线、预算、偏好纳入行程生成逻辑。
4. 支持用户对 AI 生成结果进行低成本修改。
5. 输出可保存、可分享、可线下查看的旅行方案。

### 6.3 技术目标

1. 保持 Python FastAPI + LangGraph `TripPlanningWorkflow` 后端架构。
2. 建立统一的候选 POI 评分模型。
3. 将行程生成过程结构化、可观测、可回退。
4. 为后续用户画像、对话式修改、真实交易等能力预留扩展空间。

## 7. 第一阶段范围

### 7.1 本期范围

1. 国内单城市 1-7 天游。
2. 输入城市、开始日期、结束日期、人数、每人预算、旅行偏好。
3. 城市为必填；模糊需求无城市时，只提示用户输入城市。
4. 根据景点、餐饮、住宿、天气、路线和预算生成完整行程。
5. 推荐结果包含解释理由。
6. 推荐结果根据评分/排序逻辑产生。
7. 天气不仅展示，还要影响行程安排。
8. 输出每日预算和总预算。
9. 规划完成后，用户可点击“编辑行程”，自由调整景点顺序或删除景点。
10. 用户可导出最终方案为图片或 PDF。

### 7.2 非本期范围

1. 机票、火车票、酒店、门票、打车等真实交易。
2. 用户长期画像、历史偏好学习、个性化记忆。
3. 多人偏好冲突处理。
4. 多城市跨城路线规划。
5. 实时库存、实时票价、酒店价格锁定。
6. 协作编辑、多人共享行程。
7. 商业广告推荐位。

## 8. 核心用户流程

### 8.1 规划主流程

1. 用户进入规划页。
2. 用户输入城市或包含城市的需求。
3. 用户选择开始日期和结束日期。
4. 用户设置出行人数、每人预算。
5. 用户选择旅行偏好。
6. 用户点击“智能规划”。
7. 系统校验输入，若未识别城市，提示用户输入城市。
8. 后端拆解规划任务，搜索真实候选地点。
9. 系统根据评分逻辑筛选景点、餐饮和酒店候选。
10. 系统结合天气、预算和路线生成每日行程。
11. 系统生成推荐理由、预算、天气建议和避坑提醒。
12. 用户查看行程详情。
13. 用户可点击“编辑行程”调整景点顺序或删除景点。
14. 用户导出最终行程为图片或 PDF。

### 8.2 模糊输入处理流程

| 输入示例 | 处理方式 |
| --- | --- |
| 深圳 | 识别城市为深圳，按结构化条件生成 |
| 我想一个人去深圳海边玩 | 识别城市为深圳，保留“海边玩”作为偏好补充 |
| 我想去海边玩 | 无明确城市，提示“请输入目的地城市” |
| 想去一个适合拍照的地方 | 无明确城市，提示“请输入目的地城市” |

第一阶段不做目的地城市推荐，也不根据模糊需求自动选择城市，避免用户意图不明确导致错误规划。

## 10. 推荐评分与排序逻辑

推荐结果必须经过评分和排序，而不是简单展示搜索结果。评分模型用于景点、餐饮、酒店候选筛选，并影响最终行程生成。

### 10.1 景点评分模型

景点综合评分建议由以下因素组成：

| 因素 | 权重 | 说明 |
| --- | --- | --- |
| 偏好匹配度 | 30% | 是否匹配经典、自然、拍照、历史、文艺等偏好 |
| 路线顺路性 | 25% | 与当天其他地点距离是否合理，是否减少折返 |
| POI 质量 | 20% | 评分、热度、真实坐标、地址完整度 |
| 天气适配度 | 15% | 户外景点是否适合当天天气 |
| 预算适配度 | 10% | 门票或消费是否符合预算 |

推荐理由需要基于评分因素生成，例如：

“推荐这里是因为它符合你的自然风光和拍照偏好，距离当天其他景点较近，适合安排在天气较好的上午。”

### 10.2 餐饮评分模型

餐饮不按早餐、午餐、晚餐、夜宵强制分类，重点推荐本地特色和路线顺路的餐饮选择。

| 因素 | 权重 | 说明 |
| --- | --- | --- |
| 本地特色 | 30% | 是否具有城市特色 |
| 路线顺路性 | 25% | 是否靠近当天景点或住宿区域 |
| POI 质量 | 20% | 评分、热度、真实地址 |
| 预算适配度 | 15% | 人均消费是否符合预算 |
| 偏好匹配度 | 10% | 是否匹配吃吃喝喝、小众探索等偏好 |

### 10.3 酒店评分模型

第一阶段不做真实预订，因此酒店推荐应避免承诺库存和实时价格，重点推荐住宿区域和候选酒店。

| 因素 | 权重 | 说明 |
| --- | --- | --- |
| 位置便利性 | 35% | 是否靠近地铁、景点集中区或第二天路线 |
| 预算适配度 | 25% | 是否符合每人预算 |
| POI 质量 | 20% | 评分、地址、真实坐标 |
| 路线衔接 | 15% | 是否方便开始和结束每日行程 |
| 偏好适配 | 5% | 是否符合舒适、便捷、拍照等隐性需求 |

### 10.4 行程合理性评分

生成后的行程需要进行整体评分：

| 因素 | 权重 | 说明 |
| --- | --- | --- |
| 真实性 | 25% | 地点真实存在，有坐标或可信来源 |
| 路线合理性 | 25% | 每日地点顺序合理，减少跨区折返 |
| 偏好匹配 | 20% | 行程整体符合用户偏好 |
| 时间可执行 | 15% | 每日活动数量和时长合理 |
| 预算匹配 | 10% | 总预算和每日预算不明显超标 |
| 解释完整度 | 5% | 推荐理由、天气建议、避坑提醒完整 |

## 11. 天气影响规则

天气不是单纯展示信息，而应参与规划决策。

| 天气情况 | 行程影响 |
| --- | --- |
| 小雨/中雨/大雨 | 减少海边、登山、公园、露天街区，增加博物馆、商场、展览、餐饮 |
| 高温 | 减少正午户外活动，增加室内休息和早晚户外 |
| 低温/大风 | 减少长时间户外停留，增加交通便利和室内点位 |
| 晴天/多云 | 优先安排自然风光、海边、拍照、城市步行 |

当天气数据不完整时，应展示提示：“天气数据可能变化，出行前请再次确认。”

## 12. 预算需求

预算以用户输入的“每人预算”为基础，结合人数和天数计算。

系统需要输出：

1. 总预算。
2. 每日预算。
3. 预算拆分建议：住宿、餐饮、交通、门票/活动、其他。
4. 若行程明显超过预算，需要提示风险。

第一阶段不要求精确到实时票价或酒店库存价格，预算为规划估算。

## 13. 避坑提醒

避坑提醒作为行程结果中的独立模块展示。

提醒类型包括：

1. 天气风险：下雨、高温、大风等。
2. 开放时间风险：博物馆、展馆、公园、景区可能闭馆或限流。
3. 预约风险：热门景点可能需要提前预约。
4. 人流风险：节假日、周末、热门商圈可能拥挤。
5. 交通风险：跨区移动、晚高峰、景区周边拥堵。
6. 预算风险：热门餐厅、门票、酒店区域可能超预算。

开放时间第一阶段采用“有数据则使用，无数据则提示出行前确认”的策略。

## 14. 非功能需求

| 类别 | 要求 |
| --- | --- |
| 可用性 | 外部服务失败时应给出友好提示，不应白屏或卡死 |
| 稳定性 | 行程生成失败时支持重试 |
| 性能 | 常规 1-3 天游应尽量在可接受时间内返回结果 |
| 可解释性 | 核心推荐必须有推荐理由 |
| 真实性 | 推荐地点应来自真实 POI 或可信数据源 |
| 安全性 | 用户输入和导出内容需避免注入风险 |
| 可观测性 | 后端需记录生成步骤、失败原因、外部 API 状态 |
| 可扩展性 | 为后续用户画像、多城市、交易闭环预留结构 |

## 15. 系统架构建议

### 15.1 后端架构

后端继续采用 Python 技术栈：

1. FastAPI：提供 API 服务。
2. TripPlanningWorkflow：Plan-Execute-Replan 旅行规划工作流。
3. Planner：理解需求并生成工具行动计划。
4. Executor：调用天气、地图、POI、住宿和交通工具。
5. Replanner：根据工具结果决定继续查询、重规划或进入最终生成。
6. Finalizer：整合生成每日行程、预算、风险提醒和推荐。
9. Reviewer：审查重复、绕路、预算和完整性。
10. Weather/Budget/Export Service：处理天气、预算和导出。

### 15.2 前端架构

小程序端重点页面：

1. 规划页：城市、日期、人数、预算、偏好输入。
2. 生成页：展示规划进度和失败重试。
3. 行程详情页：展示每日行程、推荐理由、天气、预算和提醒。
4. 编辑行程页：调整景点顺序、删除景点。
5. 导出页：预览导出内容，生成图片或 PDF。
6. 历史行程页：查看已保存行程。

## 16. 验收标准

### 16.1 输入验收

1. 用户输入“深圳”并选择 3 天日期，可正常生成深圳行程。
2. 用户输入“我想去深圳海边玩”时，系统识别城市为深圳。
3. 用户输入“我想去海边玩”时，系统提示输入城市，不进入生成流程。
4. 用户选择超过 7 天时，系统提示当前仅支持 1-7 天游。

### 16.2 规划验收

1. 生成结果包含每日行程。
2. 生成结果包含景点、餐饮、住宿建议。
3. 生成结果包含每日预算和总预算。
4. 生成结果包含天气信息，并体现天气对行程安排的影响。
5. 核心推荐包含推荐理由。
6. 推荐顺序符合评分逻辑，不是简单按搜索返回顺序展示。
7. 行程中不应出现明显重复地点。
8. 行程不应出现明显跨城市错误。

### 16.3 编辑验收

1. 用户可以进入编辑行程。
2. 用户可以调整同一天内景点顺序。
3. 用户可以删除某个景点。
4. 编辑后的行程可保存为最终方案。

### 16.4 导出验收

1. 用户可以导出图片。
2. 用户可以导出 PDF。
3. 导出内容使用编辑后的最终行程。
4. 导出内容包含城市、日期、每日安排、预算、天气和提醒。

## 17. 迭代路线

### 17.1 MVP 阶段

1. 完成国内单城市 1-7 天游规划。
2. 完成城市必填和模糊需求提示。
3. 完成推荐评分排序。
4. 完成天气影响行程。
5. 完成每日预算和总预算。
6. 完成编辑行程：排序、删除。
7. 完成图片/PDF 导出。

### 17.2 增强阶段

1. 支持用户对生成结果进行自然语言修改。
2. 支持新增景点、跨天拖拽。
3. 支持更准确的开放时间和预约提醒。
4. 支持用户历史行程和偏好画像。
5. 支持推荐解释更细粒度展示。

### 17.3 生产级阶段

1. 支持多城市路线规划。
2. 支持多人偏好冲突调和。
3. 支持酒店、门票、交通真实交易跳转。
4. 支持实时价格、库存和开放状态。
5. 建立用户反馈闭环，根据用户行为优化推荐。
6. 建立完整监控、评测和推荐质量仪表盘。

## 18. 风险与对策

| 风险 | 影响 | 对策 |
| --- | --- | --- |
| POI 数据为空 | 无法生成真实地点 | 增加多关键词搜索和兜底查询 |
| LLM 输出不稳定 | 行程格式错误 | 使用结构化 schema、Reviewer 和重试机制 |
| 天气数据不准 | 行程建议偏差 | 标注天气可能变化，出行前确认 |
| 预算估算不准 | 用户预期落差 | 明确预算为估算，拆分费用来源 |
| 酒店无实时价格 | 推荐可信度不足 | 推荐区域 + 候选酒店，不承诺库存 |
| 用户输入无城市 | 规划失败 | 前端阻断并提示输入城市 |
| 导出内容过长 | 图片/PDF 可读性差 | 导出模板按天分页或分段 |

## 19. 成功指标

第一阶段可使用以下指标评估产品效果：

1. 规划成功率。
2. 生成失败率。
3. 用户编辑行程比例。
4. 用户导出行程比例。
5. 用户对推荐理由的满意度。
6. 用户是否认为路线合理。
7. 平均生成耗时。
8. POI 真实性命中率。
9. 预算超标提示准确率。
10. 天气影响行程的覆盖率。

## 20. 总结

“随心游”的核心不是简单推荐景点，而是把 AI 用在旅游规划中真正复杂的部分：理解用户需求、拆解任务、搜索真实候选、进行评分排序、结合天气和预算生成路线合理的每日行程，并允许用户编辑和导出最终方案。

第一阶段应控制范围，聚焦国内单城市 1-7 天游，先把“可用、合理、可解释、可编辑、可导出”的闭环做好。后续再逐步扩展到用户画像、对话式修改、多城市规划、多人协作和真实交易。
